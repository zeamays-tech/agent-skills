# 中文技术文档写作

从起草阶段就按开发者的阅读任务组织内容，使用通顺、自然、准确的中文，让读者能理解设计、执行操作或核对验收结果。

## 何时使用

- 编写或补充中文 README、运行手册、部署说明、设计文档、验收记录等时，在组织内容和起草正文前应用本技能。
- 修改、翻译、审校或润色已有中文技术文档时，同样应用这些表达规则。

## 起草时如何应用

- 先明确读者和阅读目的。README 帮助读者理解用途与开始使用；操作文档写清前提、动作、停止条件和完成信号；设计文档说明职责、接口与有依据的设计理由；验收记录区分预期、实测结果和未验证项。具体结构遵循项目约定。
- 依据已确认的需求、设计、代码或验证证据写作，先给读者当前需要的结论或动作，再补充必要条件和解释；不编造命令、步骤、原理或验收结果。
- 写每段时就应用下列表达规则，明确主语和动作，合理拆分条件，使用项目约定的术语；交付前回读查漏。

## 核心原则

- **遵守任务范围**：先读取适用的 `AGENTS.md` 和项目术语约定；仅编写或修改用户授权的文档，审查请求只报告问题。
- **表达规则不改变技术事实**：命令、协议值、步骤和验收条件以项目权威来源为准；不为语言通顺改变其含义。任务明确要求的内容更新按其授权和依据执行。
- **润色时保留原意**：仅做表述优化时，不修改命令、脚本、代码块、协议值、链接目标、步骤顺序，不增删步骤或验收条件；已有原理、操作目的和设计理由保留原位置与含义，不自行补充、删减或迁移。
- **先确认含义**：根据上下文确认主语、条件、时间范围及结论强度。无法消除歧义时报告疑问；已有原文保留，起草内容中的缺失事实不作确定性陈述。

## 写作规则与示例

起草时直接采用清晰的表达；修改已有文档时先确认示例改法与原意相符。

| 问题 | 原文示例 | 建议写法 |
| --- | --- | --- |
| “拥有”式责任归属（owned by 直译） | `由部署脚本拥有` | 按归属对象改为 `由……负责 / 维护 / 规定 / 定义`；仅“持有权限/凭据”等真实所有义保留 `拥有` |
| 一逗到底的长句 | 多个动作与条件连成一句 | 拆成短句或列表，每句只讲一件事 |
| 生硬的直译 | `执行一个对配置文件的检查` | `检查配置文件` |
| 否定连用或双重否定 | `不能不保留备份` | `必须保留备份`；仅用于普通说明，安全或权限禁令按下文原样保留 |
| 动作表达不清 | `数据库、Redis、配置和数据保留` | 上下文已明确是操作要求时，改为 `保留数据库、Redis、配置和数据`；不改成 `保持不变` |
| 中英文混排缺空格或多余空格 | `空业务 CNAME或不一致`、`的 健康镜像` | `空业务 CNAME 或不一致`、`的健康镜像` |
| 同一概念术语不统一 | 混用 `可信终端` 与 `受信终端` | 确认指同一概念后，按项目术语约定在授权范围内统一；约定不明或范围外的不一致只报告，历史记录和引用保留其原有语境 |

## 保留技术边界

准确传达安全、权限和验收约束，引用报错时保留原文。仅做润色时，安全或权限禁令及会改变验收条件的措辞原样保留。

## 调用与接入

支持命名调用的客户端可使用：

```text
使用 $chinese-technical-writing 根据已确认的设计编写中文部署说明，从起草时应用表达规则。
使用 $chinese-technical-writing 审查指定中文文档，只报告问题，不修改文件。
使用 $chinese-technical-writing 润色指定中文文档，保留原意、技术约束和已有设计说明。
```

需要持续应用时，可在消费仓库的 `AGENTS.md` 中加入并按项目范围调整：

```markdown
编写、修改、翻译或审校中文技术文档时，使用 $chinese-technical-writing。
在组织内容和起草正文前加载并应用其规则，写作过程中持续遵循。
遵循本仓库的术语约定，仅编写或修改任务授权的文档；缺少事实依据或无法确认原意时报告疑问。
```

本技能可独立使用。描述字段用于兼容客户端的自动发现，不能保证每次触发；需要强制应用时使用上述仓库规则。调用技能不扩大任务的修改权限。

## 收尾

对照事实来源逐段回读，确认内容满足读者任务，条件、时间范围和结论强度有据可查；仅做润色时，还需对照原文确认原意未变。操作文档检查每步“现在做什么、何时停、通过后去哪”是否清晰。按所属仓库规则执行校验，报告编写或修改范围及仍有歧义的内容。
